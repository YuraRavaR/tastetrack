# IGDB as the game metadata source; a game is the work, not an edition, a port or a DLC

Game metadata (titles, covers, years, developers, platforms) comes from the IGDB API, run by Twitch. A catalog-backed game is an IGDB `game`, and its External Reference is (igdb, game, the IGDB numeric ID). It is one Media Item, the work across all its platforms, so a User's Log Entries for The Witcher 3 on PC and on PS5 are one Item History. IGDB "is free for both non-commercial and commercial projects", so it fits ADR-0001. Its model matches ADR-0005's Media Item: a game lists all its platforms, editions point to their game through `version_parent`, and DLC and expansions point to it through `parent_game`. (Facts about IGDB in this ADR come from its docs and the Twitch Developer Services Agreement, read on 2026-11-16, and from live calls on 2026-11-19; see `docs/research/games-metadata-source.md`. Decided in #248.)

## Considered Options

- **MobyGames** was rejected because it is paid: free API access ended in 2025, and a recurring fee breaks ADR-0001.
- **Giant Bomb** was rejected because it has had no API since its 2025 relaunch, and its API host answers non-browser clients with a Cloudflare challenge.
- **TheGamesDB** was rejected because it stores one record per game per platform, so one game would split into many Media Items, as Google Books' editions would have split a book (ADR-0011). Its keys also come with a monthly allowance.
- **RAWG** was rejected because it has only landscape images, with no portrait cover for the poster grid. Its free tier is also capped at 20,000 requests a month, and its terms don't address caching.
- **The Steam Store and the PlayStation Store** were rejected because each covers one platform, and their IDs belong to store products, not works. The Steam Store's catalog endpoints are undocumented, and the PlayStation Store has no public API.
- **Wikidata** was not adopted as a second source for Ukrainian titles: games have none (below).

## Consequences

- **Which games are Media Items.** A game is a Media Item when its `game_type` is main_game, remake, remaster or standalone_expansion, it has no `version_parent`, and its `game_status` is not cancelled. Search hides everything else: editions (Deluxe, Collector's, Enhanced, International), whether kept as versions or as `expanded_game`, along with ports, forks, DLC (dlc_addon), expansions, bundles, packs, mods, episodes, seasons and updates. A remake, a remaster and a standalone expansion are Media Items of their own, so a User rates the Final Fantasy VII they played apart from the other one. DLC and expansions can become Media Items later without a migration, since they are IGDB games with their own IDs.
- **Requests.** Every request is `POST https://api.igdb.com/v4/games` with an Apicalypse text body and the headers `Client-ID` and `Authorization: Bearer <token>`. IGDB answers browsers with CORS errors, so only the Worker calls it. The rate limit is 4 requests a second with up to 8 open, per key.
- **Search** is one request: `search "<query>"`, with the Media Item filter above in its `where` clause, so the result limit counts only games that are shown. It asks for each game's name, `first_release_date`, platform abbreviations and cover. There is one language: a Cyrillic query is sent as typed. It matches only the Russian alternative names IGDB has for some games, so "сталкер" finds S.T.A.L.K.E.R. and "відьмак" finds nothing. The UI then suggests the English title.
- **Titles.** IGDB's `name` is both the Original Title and the English Localized Title, and a game has no Ukrainian Localized Title: IGDB holds no Ukrainian names, and most games keep their English title in Ukraine. Display follows ADR-0004's rules with one title. A Manual Media Item of type game has a title, an optional Original Title and a year, like a manual film.
- **Facts.** The year is the year of `first_release_date`, the first release on any platform in any region. The developer is the first of the game's `involved_companies` flagged `developer`. The platforms are all the game's platforms, each shown by its `abbreviation`, or by its `name` when it has none.
- **Details.** Adding a game is one request with the fields expanded: name, `first_release_date`, platforms, `involved_companies` with their companies, genres, `summary`, `url`, cover, artworks and screenshots. The game's part of the cache's type-specific `extra` (ADR-0011) holds the year, the developer, the platforms, the genres, the summary, the IGDB `url` and the banner's image ID: the first artwork, else the first screenshot, else none. As for films, the About data (summary and genres) reaches only the game's page, through its Item History, never Lists, the Library or Share Links.
- **Images** are hotlinked from `images.igdb.com/igdb/image/upload/t_<size>/<image_id>.jpg`, which answers a foreign Referer and is served with a year-long immutable cache. Covers use `cover_big` (264×374) and `cover_big_2x`, cropped to 2:3 as book covers are. The banner uses `1080p`. A cover that fails to load shows the game placeholder, and a banner that fails or doesn't exist shows the blurred cover, as a book's page does.
- **Auth and the token.** The Worker authenticates with Twitch client credentials (`POST https://id.twitch.tv/oauth2/token`) and reuses one access token. A token lasts 60 days, and an application can have only 25 active at once: going over that limit inactivates older ones. A Worker that asked for a token on every invocation would spend a subrequest each time and inactivate tokens that other invocations are still using. The token lives in a new D1 table, `source_tokens` (source, access token, expiry), added by an expand-only migration (ADR-0009). A Worker that finds no token, or one with fewer than 7 days left, asks Twitch for a new one and stores it. It does the same once after IGDB answers 401. Two Workers doing so at once is harmless, since both tokens stay active. A new token costs one extra subrequest about every 53 days.
- **Secrets.** Each deployment has its own Twitch application, with `TWITCH_CLIENT_ID` and `TWITCH_CLIENT_SECRET` set as Worker secrets, never in the repo. The key holder needs a Twitch account with two-factor authentication, and the application is registered as a Confidential client. Locally the secrets live in `.dev.vars`, and the tests point the Worker at an IGDB fake. Without the secrets, game search and add answer 502, and the rest of the app keeps working.
- **Terms.** IGDB's FAQ says: "Am I allowed to store/cache the data locally? Yes. In fact, we prefer if you store and serve the data to your end users." The Twitch Developer Services Agreement, which IGDB's free use falls under, allows storing copies only with "prior written authorization from Twitch (through these terms or otherwise)", or for 24 hours. We treat IGDB's FAQ as that authorization "otherwise". This is a judgement call, and it rests on the cache being disposable: if Twitch ends access, all cached IGDB data is purged, as the agreement requires on termination. The agreement also asks for "a clear path to the source": a game's page links to its IGDB `url`, and the UI credits IGDB with a link next to the TMDB notice and the Open Library credit.
- **Cache.** Game metadata lives in the same D1 cache as films and books and follows ADR-0004's rules: filled on add, no refresh-on-read, refreshed by the cron, and disposable. Its maximum entry age, the source property ADR-0011 introduced, is **21 days**. IGDB keeps removed or replaced images on its CDN for only 30 days, so a cover or artwork IGDB changes is replaced before its old URL breaks. The cron's week-old queue refreshes game entries long before 21 days. An entry it couldn't refresh for 21 days reads as missing and is refetched by the next page that shows it.
- **Cron budget.** Adding or refreshing a game costs one subrequest, as a film does, within the cron's 40 a run across all sources (ADR-0011).
- **Unavailable games.** IGDB answers an empty array, not a 404, for an ID it doesn't have. That empty answer counts toward unavailability, as TMDB's 404 does, under ADR-0004's rule of 3 checks at least 24 hours apart. A 429, a 5xx or a timeout is temporary and never counts. A 401 refreshes the token once (above). A 401 after that, or a 403, is an access problem: as for TMDB, it alerts the Operator and never triggers conversion. A converted game copies its title and year.
- **No webhooks.** IGDB can call a webhook on create, update and delete, but the cron already finds changes and deletions, as it does for TMDB. A webhook would add a public endpoint to secure and D1 writes on every IGDB change, for no gain at this scale.
- **The schema keeps changing.** IGDB moved its enums to tables and removed the old fields after a migration window (`category` became `game_type`, and `status` became `game_status`). The IGDB source module is the only code that knows these names (ADR-0005), so the next such change is fixed in one place.
- **Out of scope for now:** Progress for games (hours or percent), a platform on a Log Entry or an In Progress, a platform filter in Search, time to beat, storylines, IGDB ratings, franchises, store links and Wikidata. A platform a User played on belongs in their Review or a Thought.
